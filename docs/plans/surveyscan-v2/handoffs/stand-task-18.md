# Задание №18 для локального Claude (стенд awm.local): приёмка E2 — безагентный сбор (C24.01–C24.03, часть)

**Цель:** доказательства для приёмки E2 по безагентному сбору — один узел, несколько источников → **один актив**,
история и ответственные не теряются, неоднозначность видна (C24.02); длительный прогон без ложного «пропал» и
повторов (C24.03); честная матрица «проверено / не проверено» (C24.01). Агентская часть E2 — **после Rust-агента**
(C52.02), не в этом задании. Сетевые устройства на железе — когда будет коммутатор.

**Когда:** после №15–16 на той же выкладке (или новее с зелёным CI); раздел 4 (длительный прогон) идёт фоном
параллельно с другими заданиями. Правила — как всегда: sudo и изменения на узлах — только с «да» пользователя;
DC — только чтение; ничего вне 10.170.108.0/24; секреты и сырой инвентарь в отчёт не попадают.

## 1. Исходное состояние
`pilot_report.py` (или «Источники данных» / «Обследования сети»): список целей сбора (SSH .5/.7/.10, WinRM win-ar,
SNMPv3 — если есть), их последние сборы, число активов. Записать UID активов узлов, которые участвуют ниже.

## 2. Один узел — несколько источников (C24.02)
Для **одного Linux-узла** (например .5 или .7 — на стенде .10 это Windows; с «да» пользователя):
1. Сбор по SSH (цель уже есть) → актив A.
2. Обследование подсети находит этот же узел → в «Обследованиях» он «в реестре» → ссылка ведёт на актив A.
3. Portable-аудит **на этом же узле** (Linux, с шифрованием, команда из Web) → загрузка → данные в **актив A**,
   не новый актив. В карточке A — оба источника в «Записях источников».
Для **win-ar**:
4. Сбор по WinRM (цель есть) → актив W. Portable на win-ar (Windows-версия, с «да» пользователя) → данные в W.
5. «Разбор конфликтов»: если что-то не сопоставилось однозначно — запись видна в очереди разбора, а не создан
   тихий дубль. В отчёт — что было в очереди.
В отчёт: UID активов до/после, число активов (не выросло), снимки «Записей источников».

## 3. Смена имени и адреса (C24.02, «база оценки»)
С «да» пользователя, на одном **тестовом** Linux-узле (не DC, не win-ar):
1. Сменить hostname → «Собрать сейчас» → тот же актив, в истории — смена имени; ответственный не потерян.
2. Если можно без ущерба для стенда — сменить IP (или DHCP-резерв) → обследование + сбор → тот же актив (сопоставление
   не по одному IP), присутствие: старый адрес — «пропал» не раньше 3 обследований, новый — «в сети».
3. Вернуть имя и адрес.
Клон ВМ без sysprep — только если у пользователя есть гипервизор и он согласен: клонировать тестовый узел, собрать
клон → **отдельный** актив или запись в разборе (одинаковый machine-id виден как неоднозначность), не слияние молча.

## 4. Длительный прогон (C24.03) — 72 часа фоном
1. Зафиксировать **до старта** (в отчёт): цели, интервалы сбора, расписание обследований, число узлов.
2. Ничего не трогать 72 ч, кроме: один раз за прогон, с «да» пользователя, — выключить collector на 30 мин
   (обрыв) и включить; один раз — перезапустить центр (`vm_center` / служба).
3. Раз в сутки — `pilot_report.py` в отчёт: сборы прошли/ошибки по целям, рост числа активов (должен быть 0),
   дубли/конфликты, ложные «пропал» (узлы не выключались — должно быть 0), очередь доставки (не растёт), диск.
4. После прогона: `warehouse verify` — пусто; «Уведомления → не доставлено» — 0 (если подписка была); журнал
   центра — нет повторяющихся ошибок.

## 5. Матрица (C24.01)
По шаблону `docs/plans/surveyscan-v2/handoffs/C24-matrix.md` — новая колонка «стенд, №18»: для каждого адаптера
(SSH, WinRM, SNMPv3, обследования, присутствие, portable Linux/Windows, схема сети) — LIVE / не проверено / не
применимо, с номером раздела отчёта. Ничего не помечать «проверено» без доказательства в отчёте.

## 6. Отчёт
Разделы 1–5, отдельно итоги 72 ч (по суткам), список «не проверено» с причиной (агент — после Rust; коммутатор —
позже; Windows 11 — нет машины; rpm/apk вживую — нет узлов). Временный sudoers удалён — да/нет.

## 1. Копия и выкладка
Как в №14: свежая копия (`surveyscan-stand-backup.service` + `checkpoint.py verify` — OK, без неё не продолжать),
`git checkout <коммит>`, `make build`, центр через vm_center `--persistent --backup-marker …` (**68** миграций), новые
агент/collector в `/opt/surveyscan`, перезапуск служб (sudo), Web из коммита (`npm ci && npm run generate && npm run
build` → `~/ss-web`, `version.json` — коммит). Ctrl+F5. В меню — «Обращения» (вкладки «Очередь», «Календарь изменений»,
«Каталог услуг», «SLA»).

## 2. Подготовка (пользователь в Web)
1. «Оргструктура»: синхронизация AD проходит (кнопка полной синхронизации), в «Люди и команды» есть:
   **сотрудник А** и **руководитель Б** — обычные учётки AD, пароли знает пользователь; команда ИТ (например,
   «Служба поддержки»), в ней — оператор. Если у оператора и администратора нет записи в оргструктуре, связанной
   с их учётной записью, — связать (иначе «Взять себе» недоступно).
2. «Обращения → SLA»: проверить часовой пояс (по умолчанию Europe/Moscow) и рабочие часы (пн–пт 09:00–18:00).
   Для проверки в пределах сессии временно поставить инциденту **P1: реакция 0,2 ч (12 мин), решение 1 ч**,
   сохранить. В отчёт: понятна ли форма.
3. «Обращения → Каталог услуг» (администратор): услуга **«Выдать ноутбук»** — поля «Диагональ» (выбор: 14; 16,
   обязательное) и «Обоснование» (текст); согласующий — **руководитель Б**; команда-исполнитель — ИТ; выдача со
   склада — позиция «Ноутбук» из №14 (на складе должен быть свободный экземпляр; если нет — оформить приход).
   Вторая услуга **«Сброс пароля»** — без согласования, без склада.

## 3. Портал сотрудника на реальном AD (W3-01, W3-09)
1. Выйти. На странице входа — «Сотрудникам: обращение в ИТ — войти учёткой AD». Сотрудник А входит как `логин`,
   затем (после выхода) как `AWM\логин` — оба работают. Неверный пароль — «не удалось войти»; серия неверных подряд —
   ограничение попыток (в отчёт: после скольких, текст сообщения).
2. На портале нет реестра, склада, очереди. Проверить сервером (браузер сотрудника, адресная строка или curl с его
   cookie — **cookie в отчёт не класть**): `/api/v1/assets`, `/api/v1/warehouse/units`, `/api/v1/itsm/tickets` → 403.
3. Сотрудник А: «Сообщить о проблеме» — «Не печатает принтер» (мешает работе). Номер `INC-…`.
4. Оператор в Web (обычный вход): обращение в «Очереди» с колонкой SLA («до ЧЧ:ММ»); «Взять себе»; внутренний
   комментарий «проверить драйвер» и публичный «Перезапустите принтер, пожалуйста»; «Ждём заявителя».
5. Сотрудник А: видит публичный, **не видит** внутренний комментарий; отвечает «не помогло». Оператор: «В работу» →
   «Решён…» с решением. Сотрудник А: «Не решено» → обращение снова в работе (повторно открыто: 1); оператор решает
   снова; сотрудник — «Решено, спасибо» → закрыто.
6. Руководитель Б входит на портал и **не видит** обращение сотрудника А (список пуст или без него).
В отчёт: снимки портала (без ФИО), удобство, непонятные надписи.

## 4. Инциденты, проблемы, назначение (W3-02…04)
1. Оператор регистрирует инцидент с привязкой к активу стенда (UID из карточки) и **P1** (влияние и срочность —
   высокие) → передать команде с причиной «эскалация» → решить → закрыть. Журнал карточки: создание, назначения,
   переходы.
2. Два оператора (или две вкладки разных учёток) одновременно жмут «Взять себе» на новом инциденте — назначение одно,
   второй получает «Карточка изменилась».
3. Проблема «Сбой драйвера печати» → связать с инцидентом из п. 3 раздела 3 (связь «обращение») → «Расследовать» →
   «Известная ошибка…» с обходным решением → в карточке инцидента видно «Обходное решение».

## 5. Заявка со склада (W3-05)
1. Сотрудник А на портале: «Заказать услугу» → «Выдать ноутбук» → без «Диагонали» отправить нельзя; заполнить →
   «на согласовании».
2. Руководитель Б на портале: блок «Ждут вашего согласования» → «Согласовать». Сотрудник А в это время не может
   согласовать сам себе (кнопки у него нет).
3. Оператор: карточка `REQ-…` → блок заявки: «Согласовано»; «Выдать со склада» — выбрать экземпляр → «Выдать и
   исполнить» → состояние «исполнена», связь «склад: акт …». Повторно нажать (если кнопка ещё видна во второй
   вкладке со старой карточкой) — отказ, второй выдачи нет. «Склад → Экземпляры»: ноутбук числится за сотрудником А;
   акт выдачи открыть и сохранить PDF (основание «Заявка REQ-…»).
4. Сотрудник А: «Получено, спасибо» → закрыто.
5. Вторая заявка «Выдать ноутбук» → руководитель Б «Отклонить» без причины — нельзя; с причиной — «отклонено».
6. «Сброс пароля» → сразу «выполняется» (без согласования); оператор «Исполнено…» → сотрудник подтверждает.

## 6. Изменения и календарь (W3-06)
Только записи в центре — **ничего на серверах не менять**.
1. Оператор: «+ Обращение» → вид «Изменение» «Обновление прошивки (учебное)», связь с активом стенда → окно завтра
   10:00–12:00, риск средний, план и план отката → «На согласование» → у оператора кнопки согласования нет
   («ждёт согласования администратором»), администратор «Согласовать изменение» → «Запланировать».
2. Второе изменение на **том же активе**, окно 11:00–13:00 → согласовать → «Запланировать»: предупреждение о
   пересечении с первым; отказаться → состояние не меняется; повторить и подтвердить → «запланировано», в окне
   «пересечение подтверждено».
3. «Календарь изменений»: оба окна на завтра, листание «2 недели →/←».
4. Первое: «В работу» → «Выполнено…» с результатом проверки → «Закрыть». Второе: «В работу» → «Откат…» с причиной →
   «Закрыть»; связать с ним новый инцидент «после работ пропала связь».

## 7. SLA (W3-07) — в рабочие часы
1. Сразу после п. 2 раздела 2 (P1: реакция 12 мин) создать инцидент P1 и **ничего с ним не делать**. Через ~10 мин
   (80 % срока) в очереди — «скоро срок», в карточке «Реакция: скоро срок», в журнале — «SLA реакции: скоро срок»;
   через ~13 мин — «нарушен». Записать время каждой отметки (проход фоновой роли — раз в минуту).
2. «Взять себе» → реакция «просрочен», решение идёт; «Ждём заявителя» на 5 мин → «пауза», прошедшее время решения не
   растёт; «В работу» → «Решён…» → решение «в срок».
3. Если сессия идёт вне рабочих часов: срок не должен расти (проверить на открытом инциденте за 10 мин) — в отчёт.
4. Вернуть сроки SLA к значениям по умолчанию (или к тем, что назовёт пользователь).

## 8. События во внешние системы (W3-08)
1. На ВМ центра в отдельном окне: `python3 v2/scripts/webhook_sink.py --port 18080` (слушает только 127.0.0.1).
2. «Уведомления» (если выключены — «Включить уведомления»): подписка `http://127.0.0.1:18080/itsm` на все пять
   событий обращений («Новое обращение», «Смена состояния обращения», «Назначение обращения», «SLA: скоро
   нарушение», «SLA: нарушение срока»). Ключ подписи показывается один раз — **не копировать в отчёт**.
3. Создать инцидент, взять, решить → в окне приёмника строки `ticket.created.v1 …`, `ticket.assigned.v1 …`,
   `ticket.state_changed.v1 …` с номером обращения; в строках нет текстов обращений.
4. Повторная доставка: остановить приёмник, запустить с `--fail 2`, сменить состояние обращения → первые 2 ответа
   500, затем 204 с отметкой **ПОВТОР** и тем же event_id; в «Уведомления → Доставки» — «доставлено», попыток 3.
5. Остановить приёмник; подписку отключить («Отключить»).

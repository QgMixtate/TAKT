## 3. KVM на Linux-ВМ стенда
1. Узел — **.5 (mvp)**; если на .5 нельзя (мало ресурсов/запрет) — спросить пользователя, на какой. Вложенная
   виртуализация не нужна: проверяем по **выключенным** ВМ (libvirt показывает их в `list --all`).
2. Установить (с «да» — дано): `apt-get install -y --no-install-recommends libvirt-daemon-system libvirt-clients qemu-system-x86`
   (или аналог для ОС узла). Сеть `default` libvirt — оставить выключенной (`virsh net-autostart default --disable`),
   чтобы не появился мост 192.168.122.0/24 и NAT на узле; если сеть уже запущена пакетом — `virsh net-destroy default`.
3. Учётке SSH-цели .5 (та, под которой собирает collector) дать **только чтение libvirt**: группа `libvirt`
   (`usermod -aG libvirt <учётка>`) — и проверить под ней: `virsh --readonly -c qemu:///system list --all`.
4. Определить (не запускать) две тестовые ВМ: `t24-web` (2 vCPU, 1 ГБ, диск-файл 1 ГБ в пуле `default`, интерфейс в сети
   `default`) и `t24-db` (1 vCPU, 512 МБ, без диска): `virt-install --print-xml` или XML вручную → `virsh define`. Пул
   `default` — каталог `/var/lib/libvirt/images`. ВМ **не запускать**.
5. В отчёт — команды и вывод `virsh --readonly list --all`, `net-list --all`, `pool-list --all` (без секретов).

## 4. Проверка C57
1. В течение ~1 мин после старта collector (затем раз в период цели, не чаще 15 мин) — в журнале collector
   `target_<id>_kvm_snapshot_sent`; при `kvm_unavailable` / `kvm_snapshot_rejected` — причина.
2. Web → «Платформы»: платформа KVM «<имя .5>», объекты: хост, 2 ВМ (выключены), сеть `default`, пул `default`;
   «не обследованы» — 2 ВМ (внутри них агента нет — так и должно быть). Скриншоты.
3. Карточка хоста .5: блок «Платформа» — не появится (это сам хост KVM; блок — у ВМ, сопоставленных с активом); проверить,
   что в «Платформах» объект «хост» KVM имеет ссылку «карточка хоста» **или** «не обследован» — записать, что видно
   (сопоставление хоста KVM по UUID требует, чтобы SSH-сбор .5 отдавал BIOS UUID — фиксируем факт).
4. Удаление: `virsh undefine t24-db` (с «да» — дано в п. 3, тестовая ВМ). Через 3 сбора KVM (≈45 мин при периоде
   15 мин; можно «Собрать сейчас» на цели .5 трижды с интервалом) — `t24-db` «удалён из платформы». Скриншот.
5. Компьютеры AD: после ближайшей **полной** синхронизации каталога (раз в сутки; можно «Синхронизировать сейчас»
   с полной синхронизацией, если доступно в Web) — платформа «Active Directory»: компьютеры домена (DC, win-ar, …),
   у win-ar и DC — «карточка хоста» (сопоставление по имени). Скриншот. DC — только чтение.
6. Раздел «Платформы» — пустых/сломанных экранов нет; «не обследованы» — фильтр работает.
6а. Исправления №84–93 (да/нет, скриншоты): аудит ручной привязки; правило «Windows» — заменить образец на
   «ВМ Windows» (virtual_machine/windows) **с «да»**, 3 прежних предложения — отклонить **с «да»**; простой центра при
   ручной копии (ожидание — единицы секунд + запуск); карточка win-ar 12/12 после WinRM; модель .5 и task11;
   цвет площадки = цвету «Стенда»; «Применить правила» — хостов 6; знаменатели разделов одинаковы.
7. Hyper-V (C57.02 ч. 3): на WinRM-целях (win-ar, DC) collector раз в период выполняет **только чтение** CIM
   `root\virtualization\v2`; роли Hyper-V на стенде нет — в журнале collector не должно быть `hyperv_snapshot_*`,
   платформа Hyper-V в Web не появляется, на узлах ничего не меняется. Записать, что видно.

# C54 — ресурсно-сервисная модель (РСМ): системы, среды, компоненты, хосты (проект, решения пользователя 2026-11-19)

Основание: требования пользователя 2026-11-19 к C53 («кому нужны индивидуальные хосты, прежде всего нужно видеть
системы; хост — финальный этап разворачивания»; «РСМ нету»; дерево «компания → площадки → системы → … → метрика»).
Макеты: [C53-mockups](C53-mockups/) 6–9, 12. Статусы и счётчик в plan.json не меняются. C03 не меняется (новых типов
событий нет — изменения РСМ идут в аудит и историю модуля, как в C26). Миграции — только следующими номерами.

## Решения пользователя (2026-11-19)
- **Наполнение:** все три способа — вручную в Web, импорт CSV/Excel, правила автопривязки с подтверждением оператором.
- **Уровни:** фиксированные — Направление (необязательно) → Система → Среда → Компонент → Хост.
- **Общие хосты:** да, хост может входить в несколько систем с пометкой «общий»; одна привязка — основная.
- **Сервисы C26 = системы:** существующие сервисы становятся системами с теми же идентификаторами и связями;
  `/api/v1/services` сохраняется.
Проект целиком (разделы ниже) ждёт «да» пользователя перед кодом.

## 1. Что есть сейчас (C26) и чего не хватает
Есть: `cmdb.services` (бизнес-сервис: имя, критичность, владелец), `cmdb.relations` (`runs_on`, `uses`,
`depends_on`, `hosts`, `connected_to`), классы активов (server, workstation, network_device, printer,
virtual_machine), площадки и сетевые области (`scope.sites`, `scope.network_scopes`), ответственные (только на активах).
Нет: сред, компонентов (ролей) системы, привязки хостов к компоненту, эталона компонента, групп систем
(направлений), ответственных у системы, правил автопривязки, сводного состояния по дереву, очереди «хосты вне систем».

## 2. Модель
```
Направление (группа систем, необязательно)
└─ Система (= развитие сервиса C26: service_uid сохраняется)
   ├─ критичность, владелец (бизнес), ответственный ИТ, окно обслуживания, площадки (вычисляются по хостам)
   ├─ Среда: прод | тест | разработка | DR | … (справочник)
   │  └─ Компонент (роль): «Сервер приложений 1С», «СУБД», «Балансировщик», «СХД»…
   │     ├─ эталон: ожидаемые ОС, версии ПО, антивирус, порты, локальные админы (необязательно)
   │     └─ Хосты (активы C25): основная привязка + доп. привязки
   └─ Зависимости: система → система (`depends_on`), компонент → компонент (`uses`)
```
- **Хост в нескольких системах** (общий кластер СУБД): разрешено; у привязки есть флаг «общий». Состояние общего
  хоста влияет на все системы, где он есть.
- **ВМ и гипервизор**: связь `hosts` (из инвентаризации/vCenter позже); ВМ привязывается к компоненту, гипервизор —
  к инфраструктурной системе «Виртуализация».
- **Хосты вне систем** — отдельный вычисляемый список (очередь разбора) со счётчиком на главном экране.
- **Площадка системы** — вычисляется по площадкам её хостов (не вводится руками); дерево «площадка → система»
  показывает систему на каждой площадке, где у неё есть хосты.

## 3. Как наполняется (решено: все три способа)
1. **Вручную** в Web: создать систему/среду/компонент, привязать хосты (массово — «все по фильтру»).
2. **Импорт** CSV/Excel: «система; среда; компонент; хост|IP|маска имени» — с предпросмотром и отчётом расхождений.
3. **Правила автопривязки** (на компонент): подсеть, маска имени хоста (`msk1-app-*`), OU в AD, установленное ПО
   («есть 1С:Предприятие Server»), класс актива. Новые хосты, попавшие под правило, привязываются **предложением**
   (подтверждает оператор) или **сразу** — выбор на правиле. Конфликт двух правил → в разбор, не тихо.

## 4. Состояние (для дерева и светофора — до C55)
Пока нет мониторинга метрик, цвет считается из того, что есть: свежесть и полнота инвентаризации, присутствие (C21),
отклонение от эталона компонента, конфликты сопоставления. Правила подъёма вверх: хост → компонент (порог
«≥ N хостов» или «≥ X %»), компонент → среда → система (критичный компонент — сразу), система → площадка →
компания (учёт критичности). Метрики CPU/память/службы добавит этап мониторинга (C55) в те же правила.

## 5. Масштаб (крупный enterprise)
Счётчики дерева и списков — агрегаты, обновляемые инкрементально при приёме наблюдений и изменении привязок
(не подсчёт на лету). Списки — курсор, серверные фильтры. Пересчёт агрегатов после массовых операций — фоновой задачей.
Уточнение пользователя 19.11: «1 млн» — образ большого enterprise, не жёсткая цифра. Архитектура без потолка (агрегаты, курсоры, серверные фильтры); замер (как C30) на 100 000 хостов / 2 000 систем, цель: дерево и список систем < 300 мс.

## 6. API и Web (коротко)
`/api/v1/systems` (+ `/environments`, `/components`, `/bindings`, `/rules`, `/dependencies`, `/tree`,
`/unassigned-hosts`), If-Match, история, аудит. Web — по макетам C53: «Системы», карточки системы/компонента/хоста,
«Здоровье» (без метрик до C55). Совместимость: `/api/v1/services` C26 работает как раньше (системы = сервисы).

## Ход работ
- **C54.01 (19.11, a0f6e79):** миграция 0070, store `cmdb/rsm.go`, перенос привязок при слиянии (C25.03), тест TestC54RSMModel.
- **C54.02 (19.11):** `cmdb/rsm_rules.go` (правила, предложения, подтверждение/отклонение, путь «система; среда;
  компонент» для импорта), `app/rsm.go` (признаки хоста: имена, адреса, класс, ПО; проход правил после приёма
  наблюдения и по запросу; массовая привязка до 10 000; импорт CSV `surveyscan-rsm-bindings;1` с предпросмотром),
  тест TestC54RSMFilling. Правила:
  - auto-правила двух компонентов на одном хосте — конфликт: все совпадения идут предложениями в разбор;
  - отклонённая оператором пара правилами больше не предлагается (импорт и ручная привязка — могут);
  - маска имени сравнивается с полным и коротким именем; ПО — подстрока названия; подсеть — CIDR;
  - **ad_ou пока отклоняется:** OU каталога не собирает ни один источник; включится вместе с источником OU;
  - Excel — сохранением в CSV (разбор .xlsx без новой зависимости не делался); API и Web — C54.04.
- **C54.03 (19.11):** миграция 0071 (cmdb.host_states, cmdb.node_states — производные агрегаты), `cmdb/rsm_state.go`
  (запись/чтение состояния, страницы систем/хостов компонента/«вне систем»), `app/rsm_state.go` (расчёт и фоновая
  задача раз в 5 мин), тесты TestRSMHostColor/BaselineDeviations/Rollup и TestC54RSMState. Правила цвета:
  - хост: пропал из подсети (C21) или инвентаризация старше 7 сут — красный; старше суток, конфликт сопоставления,
    отклонение от эталона — жёлтый; инвентаризации не было — серый;
  - эталон: `os` — подстрока наблюдаемой ОС, `software` — название (подстрока) и версия (префикс); нет данных о
    хосте — не отклонение; прочие ключи (антивирус, порты, админы) — когда появятся данные (C55);
  - компонент: красных хостов ≥ 50 % — красный, есть красные/жёлтые — жёлтый; среда: критичный красный компонент —
    красная, некритичный — жёлтая; система: красными её делают только прод и DR, непрод-среды — не выше жёлтого;
    направление и компания: красными их делают только системы важности high/critical;
  - в каждом узле — «почему такой цвет» (коды причин со ссылкой на узел) и разбивка хостов по цветам;
    у компании — число «хостов вне систем».
  Паспорт нагрузки (облачная песочница, 4 vCPU, 15 ГБ, PostgreSQL стенда разработки, после ANALYZE): 100 000 хостов /
  2 000 систем / 4 000 компонентов / 95 003 привязки — пересчёт 3,6 с (запись 1,7 с, инвентаризация 0,9 с);
  чтение: узел компании 0,2 мс, страница систем «сначала проблемные» 6,2 мс (с фильтром 5,9 мс), хосты компонента
  0,3 мс, «вне систем» 2,1 мс — цель < 300 мс выполнена. Оговорка: у синтетических хостов нет фактов инвентаризации —
  на реальных данных фаза «инвентаризация» дороже; CI гоняет замер на 3 000 хостов.

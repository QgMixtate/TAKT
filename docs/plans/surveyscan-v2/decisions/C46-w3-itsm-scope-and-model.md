# C46 — волна 3: ITSM (объём, модель, процессы, критерии приёмки)

Статус: **проект на приёмку пользователя** (C46.01–C46.04). Код волны 3 (C47–C50) начинается после приёмки.
Статусы в plan.json не меняются. Основа: спецификация 0.5, раздел 25 «Волна 3»; решения пользователя 2026-11-16.

## C46.01 — объём (решения пользователя 2026-11-16)

Входят все четыре процесса — минимальный рабочий набор каждого, не «полный ITIL»:
1. **Инциденты** — «не работает»: регистрация, классификация, назначение исполнителю/команде, эскалация, решение,
   подтверждение/повторное открытие, закрытие; связь с активом, сервисом (C26) и проблемой.
2. **Заявки из каталога услуг** — портал: услуга → форма → (согласование) → исполнение → закрытие. Исполнение
   складских услуг — командами склада W2 (выдача/возврат/замена) со ссылкой на заявку, без двойной записи.
3. **Изменения** — план, окно, риск, согласование, выполнение, проверка или откат; календарь окон, влияние на
   сервисы/активы, связанные инциденты.
4. **Проблемы** — корневая причина повторяющихся инцидентов, обходное решение, известная ошибка; связанные инциденты.

Решено:
- **Заявители — все сотрудники через портал.** Вход — учёткой AD (bind к каталогу C31); при первом входе
  сотрудник из оргструктуры (субъект с `directory_login`) получает роль **requester**: видит только свои обращения
  и каталог услуг, не видит реестр, склад и чужие данные. Это **новая функция — вход по AD** (сейчас AD — только
  синхронизация оргструктуры); локальный вход операторов остаётся.
- **SLA — простые:** сроки реакции и решения по приоритету, рабочие часы организации (один календарь, без
  праздников по площадкам), пауза «ждём заявителя», предупреждение о скором нарушении и отметка нарушения.
- **Уведомления — только Web и webhook:** «Мои обращения» / «Очередь» в интерфейсе, события во внешние системы через
  существующий webhook (C31.03). Своей почты нет.

Не входит (явно): почта и входящие письма, чат-боты, база знаний как отдельный модуль (обходные решения — в
проблемах), CMDB-бейзлайны, финансы и стоимость услуг, многоуровневые календари SLA, внешние заявители без AD.

## C46.02 — сущности и границы модуля

Новый модуль `itsm` (своя схема, пишет только в неё; активы, сервисы, ответственность, склад — только читает и
ссылается по ID). **Своего каталога активов нет**: ссылки на `asset_uid` и `service_uid` (C25/C26).

| Сущность | Смысл |
|---|---|
| `itsm.tickets` | Обращение: вид (incident / request / change / problem), номер `INC-2026-000123` и т. п., тема, описание, заявитель, приоритет (влияние × срочность), состояние, исполнитель / команда, ревизия |
| `itsm.ticket_links` | Связи: актив, сервис, другое обращение (инцидент ↔ проблема, изменение ↔ инцидент), складское движение |
| `itsm.ticket_events` | Журнал обращения (только дописывается): смена состояния, назначение, комментарий (публичный / внутренний), вложение-ссылка |
| `itsm.catalog_items` | Услуга каталога: название, форма (поля), видимость по ролям, нужно ли согласование, исполнитель по умолчанию, связь со складом |
| `itsm.approvals` | Согласование: кто, решение, когда, комментарий |
| `itsm.change_windows` | Окно изменения: начало/конец, риск, план отката; конфликты окон по сервисам/активам |
| `itsm.sla_policies` / `itsm.sla_timers` | Сроки по приоритету и виду; таймеры реакции/решения с паузами |
| `itsm.business_hours` | Рабочие часы организации |

Права: **requester** (свои обращения, каталог), **operator** (очереди, обработка), **admin** (каталог, SLA, политики).
Внутренние комментарии requester не видит. Изоляция по организации — как везде.

## C46.03 — процессы (состояния) и аудит

- **Инцидент:** new → assigned → in_progress ⇄ waiting_customer → resolved → closed; resolved → in_progress
  (повторное открытие заявителем в течение 5 рабочих дней); cancelled. Эскалация — смена команды/приоритета с причиной.
- **Заявка:** submitted → (pending_approval → approved | rejected) → in_fulfillment → fulfilled → closed; cancelled.
  Складская услуга: исполнение создаёт складскую операцию со ссылкой на заявку (одна транзакция, повтор не дублирует).
- **Изменение:** draft → submitted → (approved | rejected) → scheduled → in_progress → completed | rolled_back →
  closed. Окна изменений не пересекаются на одном сервисе/активе без явного подтверждения.
- **Проблема:** new → investigating → known_error (обходное решение) → resolved → closed.
- Каждый переход — запись журнала обращения, аудит и событие для webhook (`ticket.*.v1` — новый контракт W3, вне
  замороженного C03). Конкурентное назначение — условное обновление по ревизии (второй получает 409).

## C46.04 — критерии приёмки волны 3

| AC | Сценарий | Пакет |
|---|---|---|
| W3-01 | Сотрудник входит на портал учёткой AD, видит только каталог и свои обращения; реестр/склад недоступны | C48 |
| W3-02 | Инцидент: создание с привязкой к активу → назначение команде → решение → повторное открытие → закрытие; журнал и аудит | C47 |
| W3-03 | Два оператора одновременно берут инцидент — назначение одно, второй получает конфликт | C47.04 |
| W3-04 | Проблема по трём инцидентам: обходное решение видно в инцидентах, решение проблемы закрывает связь | C47.02 |
| W3-05 | Заявка «Выдать ноутбук»: согласование → исполнение складом (акт выдачи со ссылкой на заявку) → закрытие; повтор исполнения не создаёт второй выдачи | C48 |
| W3-06 | Изменение: окно, согласование, выполнение и откат; конфликт окон на одном сервисе предупреждается | C49 |
| W3-07 | SLA: срок реакции/решения по приоритету в рабочих часах, пауза «ждём заявителя», предупреждение и нарушение | C50.01 |
| W3-08 | Webhook: события обращений доставляются, повторная доставка не создаёт дублей у получателя (идемпотентный ключ) | C50.02 |
| W3-09 | Внутренний комментарий не виден заявителю; заявитель не видит чужие обращения (проверка API, не только UI) | C46–C48 |

## Порядок реализации после приёмки
C46 модуль и схема → C47 инциденты и проблемы + рабочее место оператора → вход по AD и роль requester → C48 каталог
и заявки (со складом) → C49 изменения и календарь → C50 SLA и webhook-события, сквозная проверка и нагрузка.

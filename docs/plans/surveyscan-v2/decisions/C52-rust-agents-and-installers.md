Статус: **принят пользователем 2026-11-16** («да» после ответов на вопросы, раздел C52.05). Статусы в plan.json не меняются.
Реализация: C52.01 (коды регистрации, `register` агента и collector, Web «Установка») — сделано. C52.02 — Linux-часть: Rust-агент регистрируется по коду, шлёт heartbeat, получает профили 1.0/1.2, собирает 12 разделов Linux (парсеры — общие векторы с Go), ставит подписанный пакет в очередь и доставляет с удалением только по подписанному результату центра (rust_agent_smoke в CI). Продление сертификата — сделано (renew; Go-агент работает на обновлённой личности). Далее: Windows (служба SCM, сбор WMI/реестр, machine id из реестра), сравнение записей с Go на эталонных ВМ; служба systemd и пакеты — в C52.04; затем C52.03. Код — после приёмки. Статусы и счётчик в plan.json не
меняются до приёмки; номер C52 — предлагаемый (новый пакет по решению пользователя, как C51).

## Почему
Сейчас агент, collector и portable — программы на Go, но на площадке их нечем поставить: агент и collector
устанавливаются вручную по документации (systemd / служба Windows, `prepare` → grant → `enroll`), portable переносят
руками; Web выдаёт команды, но не программы. Нужен путь «скачал → установил → ввёл код → работает».

## C52.01 — решения пользователя (2026-11-16)
1. **На Rust переписываются агент и portable** (ставятся на каждый ПК/сервер: один файл без зависимостей, Windows и
   Linux). **Collector остаётся на Go** и получает установщики.
2. **Все способы установки:** скачивание из Web центра; Windows — MSI (в том числе раздача через GPO); Linux — deb и
   rpm; portable — один файл «на флешке» без установки.
3. **Подключение к центру — код регистрации из Web** (одноразовый или на N установок, с ограниченным сроком),
   вводится при установке или передаётся параметрами MSI/GPO.
4. **Порядок:** сначала этот проект, потом код; задания на стенде №15–16 идут параллельно.

## C52.02 — что не меняется
- **Протокол обмена с центром C03 заморожен:** Rust-агент говорит тем же wire-форматом (C03/C15: события, записи
  инвентаря, профиль, mTLS, диск-очередь), центр не отличает его от Go-агента. Формат portable-пакета — C23
  (в т.ч. шифрование HPKE ключом центра) без изменений: центр импортирует пакеты обоих.
- Регистрация по коду — **надстройка** над существующей выдачей grant (новый контракт C52 вне C03): центр по коду сам
  создаёт источник и grant, привязанный к CSR, который сгенерировал устанавливаемый агент. Закрытый ключ не покидает
  машину, как и сейчас.
- Go-агент и Go-portable остаются в поставке, пока Rust-версии не приняты; затем удаляются отдельным решением.

## C52.03 — объём и модель

### Rust-агент (Linux amd64/arm64, Windows x64)
- Режимы как у Go-агента: служба (systemd / SCM), сбор по профилю (интервалы из центра), диск-очередь при обрыве,
  повтор с тем же ID события, продление сертификата, `register`, `status`, `uninstall-cleanup`.
- Сбор: ОС, железо, ПО, службы, сеть, обновления — те же секции C15 1.2; Windows — WMI/реестр без PowerShell,
  Linux — /proc, /sys, dpkg/rpm. **Паритет проверяется сравнением** записей Rust- и Go-агента на эталонных ВМ (CI:
  Ubuntu, Debian, Rocky, Windows Server 2022) — расхождения только в допустимых полях (время, порядок).
- Статическая сборка: Linux — musl, Windows — один .exe без runtime. Подпись выпуска — тем же ключом Ed25519, что и
  остальные компоненты (release.py).

### Rust-portable (Windows x64, Linux amd64)
- Один файл: `init` (ключ, регистрация в Web — как сейчас), `collect` → пакет C23 (зашифрованный ключом центра),
  `verify`. Работает без прав администратора там, где это возможно (без прав — неполные секции помечаются).
- Режим «флешка»: каталог рядом с файлом, никаких следов в системе, кроме выбранного каталога.

### Collector (Go) — только упаковка
- Linux deb/rpm (служба systemd, пользователь `surveyscan-collector`), Windows MSI (служба SCM).
- Регистрация тем же кодом, что и агент (вид источника — collector, площадка из кода).

### Установщики
| Что | Linux | Windows |
|---|---|---|
| Агент (Rust) | deb, rpm, tar.gz | MSI (x64), zip |
| Collector (Go) | deb, rpm, tar.gz | MSI (x64), zip |
| Portable (Rust) | один файл | один .exe |

- MSI: параметры `CENTER_URL`, `REG_CODE`, `CENTER_FINGERPRINT` (тихая установка, GPO); удаление — служба и
  каталоги программы; данные очереди — по флагу.
- deb/rpm: `surveyscan-agent register --center … --code … --fingerprint …` после установки (или файл
  `/etc/surveyscan-agent/register.env` для массовой установки через Ansible и т. п.).
- Сборка всех пакетов — в CI на Linux (cargo + cross-сборка Windows, msitools/wixl для MSI, nfpm или
  dpkg-deb/rpmbuild); артефакты в выпуске подписаны.

### Скачивание из Web
- «Источники данных» → **«Установка»**: список файлов выпуска, который сейчас работает в центре (агент, collector,
  portable × ОС × формат), размер, SHA-256, подпись; кнопка «Скачать»; рядом — команда/параметры установки для
  выбранной площадки и кода.
- Файлы раздаёт центр из подписанного выпуска (не из интернета); скачивание доступно администратору и оператору,
  записывается в аудит.

### Код регистрации
- Администратор в Web: «Создать код» → площадка, вид (агент / collector), срок (по умолчанию 24 ч, максимум 30 дней),
  число установок (1 или N для GPO), комментарий. Показ кода — один раз; в центре хранится только хеш.
- Вместе с кодом показывается **отпечаток сертификата центра** — установщик проверяет его при первом подключении
  (защита от подмены центра); без отпечатка установка не продолжается.
- Устанавливаемый агент: генерирует ключ и CSR → `POST /api/v1/machine/register` {код, CSR, платформа, имя хоста} →
  центр проверяет код (срок, остаток установок, площадка), создаёт источник и grant, выпускает сертификат —
  в одной транзакции; повтор того же запроса — тот же результат (идемпотентно); исчерпанный/просроченный код — отказ.
- Отзыв кода в Web; в списке — сколько установок прошло, какие источники созданы; всё — в аудите.

## C52.05 — ответы пользователя (2026-11-16)
1. **Подпись Authenticode — нет** («не у всех заказчиков есть центр сертификации»). Windows-файлы не подписываются
   кодовым сертификатом; целостность — SHA-256 и подпись выпуска Ed25519 (проверка в Web «Установка» и `verify`).
   В руководстве — как установить через GPO/тихо и что делать с предупреждением SmartScreen при ручном запуске.
2. **ОС:** Windows 10/11, Server 2016+; Linux — Debian 11+, Ubuntu 20.04+, RHEL/Rocky/Alma 8+, **Astra Linux**
   (deb), **РЕД ОС** (rpm), **Альт** (rpm, apt-rpm). Проверка установки пакетов — в CI в контейнерах там, где есть
   публичные образы (Debian, Ubuntu, Rocky, Alma, РЕД ОС, Альт), Astra — на ВМ стенда. Ограничение: Astra в режиме
   замкнутой программной среды (проверка подписи ELF) требует подписи ключом заказчика — не входит, в руководстве —
   как добавить ключ заказчика.
3. **Windows 7 / Server 2008 R2 — не поддерживаются** (ни агент, ни portable).
4. **Go-агент и Go-portable:** после приёмки Rust-версий **убираются из поставки и из Web** (не скачиваются, не
   собираются в выпуск); исходники переносятся в каталог `old/` репозитория «на всякий случай» (без сборки в CI,
   кроме компиляции, чтобы не сгнили, — по решению при переносе). До приёмки Rust остаются как есть.

## C52.06 — требования пользователя к portable (2026-11-17, по отчёту стенда №15–16)
Сейчас portable собирает только заранее перечисленные узлы, и на каждый узел нужен свой JSON с учёткой — для
офлайн-площадки на сотни и тысячи узлов это неприменимо. В Rust-portable (C52.03) входит:
1. **Обследование подсети** без знания узлов: `discover --range 10.x.0.0/16` с исключениями, ограничением скорости и
   параллельности; результат — узлы с типом (Linux/SSH, Windows/WinRM) и портами (политика обследования — как D13/C51).
2. **Профили учёток** вместо учётки в каждом узле: один файл на аудит (SSH-ключ/пароль, WinRM доменная/локальная);
   пароли вводятся при запуске или берутся из хранилища Windows и **на диск не пишутся**.
3. **Правила привязки** «Linux → профиль 1», «Windows домена X → профиль 2», «подсеть Y → профиль 3» — **без перебора
   учёток** (не блокировать доменные учётки); узел без подходящей учётки — в пакете как «найден, доступа нет».
4. **Один запуск — один зашифрованный пакет** (C23 + HPKE): найденные узлы, инвентаризация доступных, список
   недоступных; центр показывает и недоступные узлы (как присутствие из обследования, без актива-пустышки).
5. **Лёгкий интерфейс:** локальный веб-мастер в том же exe, только 127.0.0.1, без установки: подготовка (строка из
   центра) → диапазоны и обследование → профили с проверкой на одном узле → выбор узлов и сбор с прогрессом →
   сохранение пакета со сводкой.
6. Сбор самого ПК аудитора на Windows (дефект inventory-worker исправлен в Go-portable 2026-11-17); Windows-сборка
   отдаётся из Web (C52.04) и собирается `make build`.
Контракт C23 расширяется только добавлением (узлы обследования и «доступа нет») — формат согласуется отдельным
решением при реализации; C03 не меняется.

## C52.07 — решения пользователя (2026-11-18)
1. **Удалённый сбор в Rust-portable — портировать всё:** SSH (чистый Rust, без C-библиотек) и WinRM; на
   Windows-ПК аудитора вход через встроенный Windows (Kerberos/NTLM текущей учётки или профиля), на Linux — NTLM.
2. **Формат узлов обследования** — `decisions/C23-04-portable-discovery.md`, принят «да» 2026-11-18; центр (приём, таблица, Web «Найденные узлы») — сделано, запись в Rust-portable — с обследованием подсети.
Сделано (C52.03, начало): Rust-portable `init/center-key/collect` этого хоста, пакет C23 с HPKE — Go-центр
расшифровывает и импортирует (CI).

## C52.08 — план C52.04 и решения пользователя (2026-11-26, «1а 2а 3а 4а 5а»)
Подзадачи: **04.1** deb/rpm агента (Rust) и collector (Go) → **04.2** MSI x64 (wixl/msitools в CI, проверка на
windows-2022) → **04.3** файлы выпуска в подписанном выпуске, раздача центром (админ/оператор, аудит) и Web «Установка»
со скачиванием → **04.4** задание стенду (MSI на win-ar, deb collector, portable с флешки, Astra) и руководство.
Параллельно — макет веб-мастера Rust-portable в стиле ТАКТ (код мастера — после «да» по макету).
1. Порядок — как выше (deb/rpm → MSI → Web → стенд).
2. Linux-пакеты собирает **nfpm** (один конфиг на deb и rpm; `packaging/linux/<компонент>/nfpm.yaml`).
3. В Web раздаётся **только Rust-агент**; Go-агент остаётся в tar.gz выпуска для текущих установок до приёмки Rust.
4. Макет мастера — параллельно с 04.1.
5. **Служба не стартует до регистрации:** запускается `surveyscan-<компонент>-setup` (код — параметром, переменной
   или вводом) или по `/etc/surveyscan-<компонент>/register.env` (служба `…-register`, файл с кодом удаляется после
   успеха); unit-файл службы — `ConditionPathExists` конфигурации.

### 04.1 — сделано (2026-11-26)
- Пакеты `surveyscan-agent` и `surveyscan-collector` (deb, rpm, tar.gz amd64): `/usr/bin/…`, `/usr/sbin/…-setup`,
  unit-файлы в `/usr/lib/systemd/system`, пример `register.env` в `/usr/share/<пакет>/`; пользователь службы
  создаётся при установке; `/etc/<пакет>` и `/var/lib/<пакет>` — 0700. Версия пакета — версия выпуска с «~» вместо «-».
- Обновление сохраняет регистрацию и перезапускает службу; `remove`/`rpm -e` — данные остаются; `purge` (deb) —
  удаляет регистрацию, ключи, очередь и пользователя.
- Агент — непривилегированный пользователь `surveyscan-agent` (как прежний unit-файл); collector — `surveyscan-collector`
  с `CAP_NET_RAW` (обследование ICMP), ключи collector в `/etc/surveyscan-collector` принадлежат пользователю службы.
- Сборка: `make packages` (scripts/packages.py, SHA256SUMS). Проверки: `package_smoke.py` — установка/обновление/
  удаление в контейнерах Debian 11/12, Ubuntu 20.04/24.04, Rocky 8/9, Alma 9, Альт p10 (РЕД ОС — публичного образа в
  Docker Hub нет, образ вендора подключается `SURVEYSCAN_PACKAGE_IMAGES_EXTRA`); `package_service_smoke.py` — под
  настоящим systemd с настоящими центром и collector: register.env → heartbeat агента, обновление, `collector-setup`, purge.
- Конфигурация агента читается из `/etc/surveyscan-agent/config.json` (root:группа службы, 0640), без `LoadCredential`
  — его нет в systemd 239 (RHEL/Rocky 8). Код можно передать `setup` через stdin (`echo КОД | …-setup …`).
- Прогон в песочнице 26.11: `package_smoke` — 8/8 образов; `package_service_smoke` — 6 проверок (systemd в
  привилегированном контейнере Ubuntu 24.04). В CI — на раннере с systemd; результат CI — после push.
- Ограничения: только amd64 (arm64 — после сборки Rust для arm64); Astra — на ВМ стенда (04.4).

- `packaging/windows/{agent,collector}.wxs`, сборка wixl (msitools) на Linux: `scripts/packages.py` (MSI и zip рядом с
  deb/rpm; `--only-windows`). Версия MSI — числовая: `X.Y.Z-cN[.M]` → `X.Y.(Z·1000+N).M`; MajorUpgrade с заменой и
  одинаковой версии. Без подписи Authenticode (решение C52.05).
- Параметры: агент — `COLLECTOR_URL`, `CENTER_FINGERPRINT`, `REG_CODE` (агент регистрируется через collector площадки,
  поэтому адрес — collector, а не центра); collector — `CENTER_URL`, `CENTER_FINGERPRINT`, `REG_CODE`, `LISTEN`;
  оба — `REMOVE_DATA=1` при удалении. `REG_CODE` — в `MsiHiddenProperties` (не попадает в журнал msiexec).
- Программа — `%ProgramFiles%\SurveyScan\Agent|Collector`, регистрация и очередь — `%ProgramData%\SurveyScan\agent|collector`.
  Службы `SurveyscanAgent` / `SurveyscanCollector` (LocalSystem, автозапуск) ставятся всегда; регистрация по коду —
  отложенное действие от SYSTEM до запуска служб, ошибка (неверный отпечаток, код, нет связи) — откат установки;
  служба запускается только у зарегистрированного (`start-service`), повторная установка/обновление не регистрирует заново
  (`register --if-unregistered`). Collector: правило брандмауэра Windows на программу; служба Windows у Go-collector —
  новая (`service`, `start-service`).
- Проверка: workflow `installers.yml` — сборка на Linux, `scripts/msi_check.ps1` на чистой Windows Server 2022: откат
  при ошибке регистрации без кода в журнале, установка без кода, обновление с сохранением регистрации, удаление,
  `REMOVE_DATA=1`, брандмауэр. Сквозная регистрация с центром через MSI — стенд (C52-08, win-ar).

### 04.3 — файлы выпуска и скачивание из Web (2026-11-26)
- Выпуск: `release.py build --installers .dist/packages` — MSI, zip, deb, rpm, tar.gz агента и collector и Rust-portable
  (Linux, Windows) в `payload/installers/` с `index.json`; всё — в подписанном manifest; только известные имена текущей
  версии (Go-агент не раздаётся, решение 3а).
- Центр (`internal/installers`): каталог выпуска — родитель `bin/` сервера или `SURVEYSCAN_V2_RELEASE_DIR`; подпись
  manifest — ключом `SURVEYSCAN_V2_RELEASE_PUBLIC_KEY_FILE` (если задан); каждый файл перед отдачей сверяется по размеру
  и SHA-256 с manifest (подменённый на диске — 409 `INSTALLER_INTEGRITY_FAILED`).
- API (контракт c52-registration: `InstallerList`, `InstallerFile`): `GET /api/v1/installers`,
  `GET /api/v1/installers/{имя}` — право `installers:download` (администратор и оператор, только сессия); скачивание —
  аудит `installer.downloaded` до отдачи. Миграций нет.
- Web «Установка» → «Скачать»: файлы по ОС (Windows/Linux), формат, размер, SHA-256, «Скачать»; оператор видит только
  «Скачать»; команды под пакеты (`…-setup`, `register.env`, MSI).
- Проверено: unit (каталог: подпись, подмена, чужой ключ, файл вне manifest), integration TestC52InstallersDownload
  (права, аудит, подмена → 409, контракт), release_smoke (выпуск с файлами, отказ чужой версии/имени), web smoke
  (скачивание MSI через центр, SHA-256 = manifest).

## 1. Что есть и чего не хватает

Есть (по коду): агент Go/Rust (Linux, Windows); SSH (Linux), WinRM (NTLM, Kerberos, HTTPS с закреплением
сертификата), SNMPv3 (система, интерфейсы, LLDP-соседи, MAC-таблицы — разбор есть, на стенде нет коммутатора);
обследование подсетей (ICMP, TCP-порты, ARP); LDAP/LDAPS к AD — **только люди и группы** (Оргструктура); portable;
CSV. Все удалённые цели — с collector площадки, секреты — в OpenBao, на обследуемых узлах ничего не меняется.

Не хватает: **систем управления**, которые одним запросом отдают сотни объектов и связи между ними (ВМ ↔ хост ↔
кластер ↔ хранилище), физического «железа» через BMC и полного списка машин домена. Агент/SSH/WinRM видят хост
изнутри; платформа видит то, чего изнутри не видно: на каком сервере и в каком кластере ВМ, сколько ей выделено,
выключенные ВМ, хранилища, серийники и блоки питания сервера.

## 2. Что входит в C57 и что нет

| Приоритет | Коннектор | Как | Даёт |
|---|---|---|---|
| P1 | **KVM / QEMU** | SSH (готов) + `virsh --readonly` (`nodeinfo`, `list --all`, `dumpxml`, `domifaddr`, `pool-list`, `net-list`) | хост KVM, все ВМ (вкл. выключенные), vCPU/RAM, диски, MAC, сети, пулы |
| P1 | **VMware vCenter / ESXi** | vSphere API (`govmomi`, SOAP, 443, `PropertyCollector` пакетно) | датацентры, кластеры (HA/DRS), хосты ESXi (модель, серийник, CPU, RAM, версия), ВМ, хранилища, порт-группы/vDS |
| P1 | **zVirt / oVirt** | REST `…/ovirt-engine/api` (443) к серверу управления | датацентры, кластеры, хосты, ВМ, домены хранения, сети, IP гостей (`reporteddevices`) |
| P1 | **Redfish** (iLO, iDRAC, XClarity, iBMC, Supermicro) | REST `/redfish/v1` (443) | производитель, модель, серийник, BIOS, CPU, память, диски, контроллеры, БП, сетевые порты BMC и хоста |
| P1 | **Компьютеры из AD** | LDAP/LDAPS (уже есть клиент) — объекты `computer` | имя, FQDN, ОС и версия, последний вход, OU, отключён/включён — список «что должно быть» |
| P1 | **Обратный DNS** в обследовании подсети | PTR для найденных узлов | имена найденным узлам |
| P2 | Hyper-V и Failover Cluster | WinRM (готов), PowerShell `Get-VM`, `Get-ClusterNode` | хост Hyper-V, ВМ, кластер |
| P2 | Proxmox VE | REST (8006) | узлы, ВМ/контейнеры, хранилища, кластер |
| P2 | IPMI | 623/UDP, только чтение FRU/SDR | «железо» там, где нет Redfish |
| P2 | Профили SNMP для СХД, ИБП, принтеров | SNMPv3 (готов) | модель, серийник, ёмкость/заряд/счётчики |

**Не входит** (решение — по запросу): WMI/DCOM (сложно и небезопасно без Windows-узла, WinRM закрывает Windows; только
если заказчик запрещает WinRM), NETCONF/RESTCONF/gNMI (сетевому оборудованию пока хватает SSH и SNMP), OpenStack,
Docker/Kubernetes API (контейнеры — агентом), SQL/JMX, ONVIF, mDNS/SSDP/WS-Discovery. Коннекторы к СЗИ (KSC,
MaxPatrol, UserGate, PT NGFW…) — этап ИБ/КИИ на том же REST-каркасе.

## 3. Обмен: что расширяется (нужно решение пользователя)

**Хосты и ВМ — существующим путём, без изменения C03.** Каждый объект «хост» (ВМ, гипервизор, сервер по Redfish,
компьютер AD) уходит обычным наблюдением: один источник на цель, `source_record = {namespace: "<платформа>:<id
экземпляра>", source_local_id: <moref / id / UUID>}` — так уже работают обследование и portable (много записей одного
источника). Признаки: `bios_uuid`, `mac`, `serial`, `hostname`. Данные — разделы профиля 1.2 (identity, os, hardware,
network) и **новый раздел `virtualization`** (платформа, хост, кластер, vCPU, RAM, диски, состояние питания, снимки) —
расширение профиля C15 (добавляется раздел, существующие не меняются).

**Объекты и связи — новый тип сообщения «снимок платформы» (C57-контракт, расширение обмена).** То, что не является
хостом, и связи между объектами в наблюдение не помещаются:
```
PlatformSnapshot { schema_version, snapshot_id, tenant_id, origin (источник-цель), platform (vsphere|ovirt|kvm|
  redfish|ad|hyperv|proxmox), instance (id vCenter / engine / домена), collected_at, complete: bool,
  objects[]: { ref, kind (datacenter|cluster|host|vm|datastore|network|pool|chassis|bmc), name, attrs{…} },
  relations[]: { from_ref, type (runs_on|member_of|uses_storage|connected_to|located_in|managed_by), to_ref } }
```
Подписывается и доставляется как наблюдения (тот же канал collector → центр, повтор с тем же `snapshot_id` не
дублирует). `ref` объекта-хоста связывается с активом по `source_record` его наблюдения. Полный снимок
(`complete: true`) позволяет отметить «ВМ удалена из платформы» — после 3 полных снимков подряд, как «пропал» в C21.

Решение за пользователем: **(а)** новый тип сообщения `PlatformSnapshot` в обмене collector → центр (рекомендую);
или **(б)** без расширения обмена — объекты не-хосты не хранить, связи «ВМ → хост» только в разделе
`virtualization` наблюдения ВМ (кластеры, хранилища, сети платформы в реестр не попадут — C55 их не получит).

## 4. Сопоставление

- **ВМ ↔ тот же хост от агента/SSH/WinRM:** по `bios_uuid` (SMBIOS UUID гостя). У VMware UUID в API и UUID внутри
  гостя различаются порядком байт первых трёх групп — нормализуется при приёме (обе формы → одна каноническая).
  oVirt и KVM отдают UUID как в госте. Дополнительно — MAC (сильный только вместе с другим признаком, как сейчас).
- **Гипервизор ↔ сервер по Redfish ↔ агент на гипервизоре:** по серийному номеру и `bios_uuid`.
- **Компьютер AD ↔ хост:** по FQDN (слабый признак, как имя): в карточке «есть в AD», без автослияния; компьютеры AD
  без хоста — список «в домене, но не обследован» (для обследования и отчётов ИБ).
- Конфликты — в «Разбор конфликтов», как сейчас; автослияние только по сильному признаку.

## 5. Цели сбора, права, безопасность

- Новые виды целей сбора (обследования сети → «Цели сбора»): `vsphere`, `ovirt`, `redfish`, `ldap-computers`,
  `hyperv`, `proxmox`; KVM — флажок «KVM» у SSH-цели (тот же вход, добавляется профиль команд). Расписание, «Собрать
  сейчас», последний сбор и ошибка — как у SSH/WinRM.
- Учётки — **только чтение**: vSphere — роль Read-only на корне; oVirt/zVirt — `ReadOnlyAdmin`/`UserRole` на ДЦ;
  Redfish — роль `ReadOnly`; AD — обычная учётка домена; KVM — пользователь в группе `libvirt` с `--readonly`
  (или `polkit` только на чтение). Секреты — OpenBao, в журналы и отчёты не попадают.
- TLS: проверка сертификата; самоподписанный — закрепление отпечатка при первом подключении с подтверждением
  оператора (как WinRM HTTPS). Без отключения проверки.
- Нагрузка: пакетные запросы (`PropertyCollector`, `follow` в oVirt), ограничение частоты; сбор не чаще раза в 15 мин,
  по умолчанию — раз в час.

## 6. Web

- **Карточка ВМ:** путь «платформа / кластер / хост», выделено vCPU/RAM/диски, состояние питания, снимки, хранилища.
- **Карточка гипервизора/сервера:** список ВМ, кластер, «железо» по Redfish (серийник, БП, диски).
- **Хосты:** класс «виртуальная машина» / «гипервизор» по данным платформы; фильтр «платформа», «кластер».
- **Схема сети:** уровень «Виртуализация» (кластер → хосты → ВМ). C55 получает кластеры и хранилища как объекты.
- **Источники и Цели сбора:** новые виды с формой подключения (адрес, порт, учётка, проверка доступа).

## 8. Проверка и приёмка (после «да»)

- CI без живых платформ: vSphere — официальный симулятор `vcsim` (govmomi); oVirt/zVirt и Proxmox — записанные
  ответы API (фикстуры); Redfish — эталонные ответы DMTF Redfish Mockup; KVM — `virsh` с тестовым драйвером
  (`test:///default`) по SSH в контейнере; LDAP — тестовый каталог (уже есть для Оргструктуры).
- Стенд: KVM на Linux-ВМ стенда (если разрешите поставить libvirt — с «да»); компьютеры AD — на DC (только чтение);
  vSphere/zVirt/Redfish — **нужен доступ к реальной платформе только на чтение** (есть ли у вас тестовый vCenter,
  zVirt, сервер с iLO/iDRAC?) — иначе приёмка по симуляторам с пометкой «на живой платформе не проверено».
- Критерии: ВМ платформы и та же машина от агента — **один актив**; выключенная ВМ видна; удалённая ВМ —
  «удалена из платформы» после 3 снимков; секреты не попадают в журналы; повтор снимка не дублирует.

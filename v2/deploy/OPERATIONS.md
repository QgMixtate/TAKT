# Руководство оператора SurveyScan v2 (C33.03)

Сводка процедур по ситуациям. Подробные проверенные процедуры — в [RELEASE.md](RELEASE.md), [UPDATE.md](UPDATE.md),
[BACKUP.md](BACKUP.md), [systemd/README.md](systemd/README.md). Поддерживаемые платформы — только из
[таблицы поддержки](../../docs/plans/surveyscan-v2/decisions/C33-support-matrix.md). Секреты (пароли, токены,
ключи, grant) в этот документ, тикеты и чаты не копируются — только пути к приватным файлам (права 0600).

Отметки: **[проверено]** — прогон на стенде или ВМ с протоколом; **[CI]** — автоматическая проверка;
**[не проверено]** — процедура описана, независимый прогон (C33.04) ещё не сделан.

## 1. Установка центра [проверено: 2 свежие ВМ Debian 12/systemd 252 (C13); стенд Ubuntu 24.04 — через vm_center]
1. Предпосылки: PostgreSQL 17, OpenBao 2.7.2, TLS-сертификаты edge, systemd ≥ 252, Linux amd64.
2. Проверить подпись выпуска: `release.py verify --bundle B --public-key PUB`; установить: `release.py stage`.
3. Учётные записи (sysusers), приватные конфиги 0600 в `/etc/surveyscan-server`, `LoadCredential` — по
   [systemd/README.md](systemd/README.md). Миграции — служба `surveyscan-migrate` (до сервера).
4. Первый администратор: `surveyscan-server bootstrap-admin --tenant … --password-file …` (пароль — из файла,
   не в аргументах). Площадка и резервная команда — заводятся до регистрации источников.
5. Необязательно: сервис поиска (`bin/surveyscan-search 127.0.0.1:PORT DATA TOKEN_FILE`, `search_url`/`search_token_file`
   в machine.json).
6. Хранилище секретов интеграций (один раз при установке): в политике OpenBao центра — правило
   `path "<kv>/data/server/integrations/*" { capabilities = ["create","update","read"] }`, в bao.json —
   `"integrations_path": "server/integrations"` (обвязка стенда `vm_center.py` добавляет их сама). После этого AD и
   уведомления включаются **из Web** без правки конфигурации (разделы 8, 9).
Проверка: `healthcheck`, вход в Web, `GET /api/v1/diagnostics` без предупреждений.

## 1а. Несколько экземпляров (C35) [CI: split_smoke]
Один процесс по умолчанию (`combined`). Для разделения: `SURVEYSCAN_V2_ROLE=api` — UI/API и транспорт агентов
(можно несколько за балансировщиком, у каждого свой `SURVEYSCAN_V2_LISTEN` и `listen` в machine.json);
`SURVEYSCAN_V2_ROLE=worker` — фоновая работа (можно 2 для отказоустойчивости), отвечает только на `/health/*`.
Все процессы — одна БД, один OpenBao, один сервис поиска. Сессии и задачи не теряются при остановке одного api.
**Каждому api — своя копия machine.json** (отличается только `listen`): в ней же адрес сервиса поиска и включение
протокола 1.2. api без machine.json работает, но ищет перебором по PostgreSQL — под нагрузкой это таймауты (C40.01).
За маршрутизатором ячеек (C37) несколько api одной ячейки задаются `backends` — запросы раздаются по кругу.

## 2. Обновление [проверено: C13 — проверенное обновление с откатом при неудачном старте, SIGKILL updater]
`updater.py prepare --bundle B --revocations R` → `updater.py apply --health-url …` → при сбое — автоматический
откат на прежний выпуск; незавершённое — `updater.py recover`. Схема БД только дописывается: откат после
применённой миграции — **только восстановлением из резервной копии** (раздел 3), не сменой ссылки на выпуск.
Порядок для всего контура и условия остановки — [RELEASE.md, C33.02](RELEASE.md). Отозванный выпуск не ставится.
**Web обновляется отдельно от центра** (независимая версия, C14/C40): после обновления центра пересобрать и выложить
статический Web (в `v2/web`: `npm ci && npm run generate && npm run build`; результат — `v2/web/dist/` вместе с
`v2/contracts/` → каталог показа Web; в архиве выкладки путь — `web/dist`, не `dist`) и проверить `version.json` —
иначе новые разделы и поля не появятся, а несовместимую пару Web↔API Web сам покажет как ошибку версии.

## 3. Резервная копия и восстановление [проверено: C13 — PostgreSQL, OpenBao Raft, общий checkpoint с повтором]
Ежедневно: дамп PostgreSQL + снимок OpenBao Raft + файлы состояния центра — по [BACKUP.md](BACKUP.md); хранить
отдельно от сервера; ключи OpenBao (unseal) — отдельно от копий. Восстановление — на чистую БД, затем запуск
центра (миграции догоняют), проверка входа и записи. Индекс поиска в копию не входит: пустой индекс центр
пересобирает сам (`search index rebuilt` в журнале).
- **Тайм-аут копии:** `pg_backup.py` ждёт операцию до 30 мин (было 5 — мало для базы стенда, №17–18); иначе —
  `SURVEYSCAN_PG_OPERATION_TIMEOUT=<секунды>` (60…86400).
- **Остановка центра на время копии:** общий checkpoint (копия БД + OpenBao + файлы, согласованные между собой)
  останавливает центр на время снятия — на стенде ~6 мин каждую ночь. Агенты и collector в это время копят данные
  на диске и досылают их без потерь; Web и приём недоступны. Время копии выбирать вне рабочих часов и учитывать
  в длительных прогонах (каждая ночь = ещё один перезапуск центра). Если простой недопустим — копировать только
  PostgreSQL `pg_backup.py` без остановки (он не останавливает центр), а снимок OpenBao — отдельно.

## 4. Источник перестал присылать данные
1. Web «Источники»: «последний контакт» есть, «успешный сбор» старый → сбор падает на хосте (журнал агента:
   `journalctl -u surveyscan-agent` / Журнал событий Windows, служба SurveyScan Agent).
2. Контакта нет → сеть/сертификат: с хоста `surveyscan-agent renew --config …` (обновление сертификата) [CI]; при
   отказе «unknown source» — источник отозван/удалён в центре: повторная регистрация новым grant.
3. Агент копит данные в очереди на диске и досылает после восстановления связи [проверено: C10/C15 — reconnect,
   SIGKILL, офлайн-очередь]. Переподключать (enroll заново) **не нужно** — иначе появится новый источник.

## 5. Диск заполнен [CI: реальный ENOSPC в tmpfs]
- Агент/collector: очередь ограничена `spool_limit_bytes` профиля источника и 7 сутками; при нехватке места новые
  пакеты не пишутся, служба не падает; освободить место — сбор и досылка продолжаются сами.
- Центр/PostgreSQL: остановить импорт portable-пакетов, освободить место (старые копии, журналы), проверить
  `healthcheck`. Не удалять файлы в каталогах данных PostgreSQL/OpenBao вручную.

## 6. Центр не стартует [частично проверено: откат при неудачном старте — C13]
`journalctl -u surveyscan-migrate -u surveyscan-server`: «drift»/миграция — не править схему вручную, раздел 2/3;
OpenBao sealed — распечатать по процедуре организации; «private configuration file» — права файла не 0600 или
неверный путь `LoadCredential`; `ldap_sync`/`webhook_secret_file` с ошибкой — центр не стартует намеренно
(исправить конфиг или убрать блок).

## 7. Поиск недоступен [CI: интеграционный тест C29; стенд — задание №3]
Плашка в Web — поиск работает в точном режиме по PostgreSQL. Проверить процесс `surveyscan-search`, токен-файл,
`search_url`. После перезапуска центр догоняет изменения; при смене формата — пересобирает индекс сам
(`POST /api/v1/search/rebuild` — вручную, администратор).

## 8. Синхронизация с AD [CI и демо: мок OpenLDAP по LDAPS через OpenBao; реальный AD — **не проверено**]
Включение: «Оргструктура» → «Настроить подключение к AD» → адрес `ldaps://…`, base DN, DN учётки только на чтение,
пароль (сохраняется в OpenBao, обратно не показывается), сертификат CA (PEM), при необходимости фильтр групп →
«Проверить подключение» (ничего не меняет) → «Сохранить». Блок `ldap_sync` в machine.json по-прежнему работает и
имеет приоритет (настройки в Web тогда только для просмотра). «Отключить» — люди из каталога остаются, не обновляются.
Сбои — панель синхронизации. `failed`: «bind failed» — учётка/пароль (файл `bind_password_file`);
«directory unavailable … certificate» — CA (`ca_certificate_file`); «would deactivate too many» — полный снимок
убрал бы > ¼ людей: проверить фильтры, ничего не применено. Учётка AD — только чтение.
**Служебные учётки** (Administrator, sshd, svc-*, учётки сбора) попадают в «Люди и команды», если фильтр людей
их пропускает (стенд №12). Фильтр — в настройках подключения, поле «Фильтр людей», например:
`(&(objectCategory=person)(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2))(givenName=*)(!(sAMAccountName=svc-*))(!(sAMAccountName=scan*)))`
— без отключённых учёток, только с именем (у служебных его обычно нет), без `svc-*` и `scan*`; надёжнее всего —
base DN только OU сотрудников. После смены фильтра — «Проверить подключение»: защита «> ¼ людей» не даст удалить
много людей разом.

## 9. Уведомления [CI: тестовый HTTPS-получатель; демо: включение кнопкой через OpenBao]
Включение: «Уведомления» → «Включить уведомления» (центр создаёт мастер-ключ в OpenBao; его не видно и не нужно
копировать). Подписка: адрес https получателя и события → секрет подписи показывается **один раз**.
Не доставляются:
«Уведомления» → «Доставки»: ответ получателя и следующая попытка. После 5 неудач — «не доставлено»; после
устранения причины — «Повторить» (попадает в аудит). Смена секрета подписи — новая подписка.

## 10. Ротация сертификатов и ключей [CI: TLS-ротация агента и collector с потерей подтверждения]
Агент/collector: обновление сертификата — `renew` (выполняется и автоматически до истечения); после ротации CA
центра — по [systemd/README.md](systemd/README.md) (пины CA проверяет оператор). Ключ подписи выпусков — у
ответственного за выпуск, вне серверов; при компрометации — новый ключ, новый выпуск, старые версии — в список отзыва.

## 11. Подготовка ПК Windows к сбору по WinRM через GPO [стенд №17, 18.11: проверено на win-ar, поправки ниже]
Скрипт `deploy/windows/prepare-winrm-target.ps1` нужен для одного-двух ПК. Для домена ПК готовятся групповой
политикой: один раз в GPO — дальше все ПК в OU готовы сами (новые — после входа в домен и перезагрузки).
Права учётки сбора — только чтение: она **не** администратор ПК.

**Что нужно заранее.** Доменная группа, например `SurveyScan-Collect`, в ней учётка сбора (`AWM\scanwinrm`);
адрес collector (например `10.170.108.2`); OU с ПК; общая папка, доступная на чтение «Компьютерам домена»
(обычно `\\awm.local\NETLOGON\surveyscan\`), с файлом `prepare-winrm-target.ps1`.

**GPO «SurveyScan WinRM»** (Конфигурация компьютера), привязать к OU с ПК:
1. *Настройка → Параметры панели управления → Локальные пользователи и группы* (Preferences → Local Users and
   Groups): действие «Обновить» для встроенных групп **«Пользователи удалённого управления (встроенная)»**
   (Remote Management Users, S-1-5-32-580) и **«Пользователи DCOM (встроенная)»** (Distributed COM Users,
   S-1-5-32-562): добавить `AWM\SurveyScan-Collect`. Группы выбираются из списка встроенных — работает на ПК с
   любым языком Windows.
2. *Политики → Конфигурация Windows → Параметры безопасности → Системные службы*: «Служба удалённого управления
   Windows (WS-Management)» — **Автоматически**.
3. *Политики → Административные шаблоны → Компоненты Windows → Удалённое управление Windows (WinRM) → Служба
   WinRM*:
   - «Разрешить удалённое управление сервером через WinRM» — **Включено**, фильтр IPv4 — **`*`**. Фильтр задаёт адреса
     **самого ПК**, на которых WinRM принимает подключения (не адреса клиентов): с адресом collector прослушиватель не
     создаётся (ошибка 0x80338012). Ограничение «только collector» — правилами брандмауэра (п. 4);
   - «Разрешить проверку подлинности Basic» — **Отключено**; «Разрешить незашифрованный трафик» — **Отключено**;
   - «Запретить проверку подлинности Kerberos» — **Отключено** (Kerberos нужен для сбора по HTTP 5985);
   - «Запретить WinRM хранить учётные данные RunAs» — **Включено**.
4. *Политики → Конфигурация Windows → Параметры безопасности → Брандмауэр Защитника Windows в режиме повышенной
   безопасности → Правила для входящих подключений*: TCP **5985** (Kerberos по HTTP) и/или **5986** (HTTPS),
   удалённый адрес — только адрес collector, профиль «Домен».
5. Права на чтение WMI (`root\cimv2`: «Включить учётную запись» + «Удалённое включение») групповой политикой не
   задаются — их выдаёт скрипт: *Настройка → Параметры панели управления → Назначенные задания → Немедленная
   задача (Windows 7 и выше)*, от имени `NT AUTHORITY\SYSTEM`, «Выполнять с наивысшими правами»:
   `powershell.exe -NoProfile -ExecutionPolicy Bypass -File \\awm.local\NETLOGON\surveyscan\prepare-winrm-target.ps1 -Account AWM\SurveyScan-Collect -Collector 10.170.108.2 -Gpo`
   Для сбора по Kerberos (HTTP 5985) добавьте ключ `-Kerberos`: скрипт проверит HTTP-прослушиватель, включит
   проверку Kerberos, выключит Basic и незашифрованный трафик (брандмауэр 5985 в режиме `-Gpo` — из п. 4). Без GPO
   (на одном ПК) `-Kerberos` ещё и открывает 5985 только с адреса collector.
   Ключ `-Gpo`: скрипт только выдаёт права WMI (группы, служба, прослушиватель и брандмауэр — из GPO) и
   создаёт HTTPS-прослушиватель, если на ПК есть сертификат от CA домена (автоподача, п. 6). Скрипт идемпотентен:
   повторный запуск ничего не ломает.
6. Для HTTPS с «CA домена» (без ручных PEM). **Важно:** стандартный шаблон «Компьютер» — версии 1, автоподача по нему
   не работает. Подходит одно из двух: *Политики → Конфигурация Windows → Параметры безопасности → Политики открытого
   ключа → Параметры автоматического запроса сертификатов* → шаблон «Компьютер» (проверено на стенде), или дубликат
   шаблона версии 2 с правом «Автоматическая регистрация» для «Компьютеров домена». Затем: *Политики → Конфигурация Windows → Параметры безопасности → Политики
   открытого ключа → Клиент служб сертификации — автоматическая регистрация* — **Включено** (обновлять и
   продлевать сертификаты); в AD CS — шаблон «Компьютер» (или его копия с проверкой подлинности сервера) с правом
   «Автоматическая регистрация» для «Компьютеров домена».

**Применение.** После `gpupdate /force` **не перезагружать ПК сразу — подождать около 2 минут**: перезагрузка
прерывает немедленную задачу (событие 111), и до смены версии GPO она не повторится.

**Если на ПК уже есть HTTPS-прослушиватель на самоподписанном сертификате** (ручная подготовка раньше): скрипт с
`-Gpo` перепривязывает его на сертификат CA домена, если тот выдан ПК (с версии 18.11; раньше — удалить вручную:
`winrm delete winrm/config/Listener?Address=*+Transport=HTTPS`).

**Отключение политики.** Правила брандмауэра 5985/5986 задаются GPO (п. 4) и при её отключении/отвязке **уходят** —
порты закроются, сбор остановится. Перед отключением: перевести цели сбора, либо оставить локальные правила
(`prepare-winrm-target.ps1` без `-Gpo` создаёт их на ПК).

**Проверка на ПК** (после `gpupdate /force`, паузы и перезагрузки): `winrm enumerate winrm/config/listener` — есть
прослушиватель на 5985 (и 5986, если есть сертификат домена); `net localgroup` встроенных групп — есть группа сбора.

**В SurveyScan.** Цель создаётся в «Обследования сети» → «Собирать…» у найденного узла:
- **HTTP 5985 + Kerberos** — полное имя ПК (например `win-ar.awm.local`) и доменная учётка; NTLM по HTTP не
  используется — без Kerberos сбор не начнётся; сообщения шифруются Kerberos (AES). Collector должен видеть DNS
  домена (записи `_kerberos._tcp.<домен>`) и KDC (TCP 88), часы collector и DC — расхождение не более 5 минут;
  учётка и ПК — с шифрованием AES (по умолчанию в современных доменах; RC4 не поддерживается);
- **HTTPS 5986** — проверка сертификата: «CA домена» (корневой сертификат AD CS загружается один раз на вкладке
  «Учётки сбора»), «запомнить при первом подключении» или PEM конкретного ПК.

## 12. Узлы с двухфакторным входом по SSH [стенд: узел .6]
Если на узле вход требует второй фактор (код, OTP), сбор по SSH невозможен: в «Цели сбора» —
«узел требует второй фактор входа». Разрешите учётке сбора вход **только по ключу** без второго фактора, не
ослабляя остальных: в `/etc/ssh/sshd_config` в конце
```
Match User scanprobe Address 10.170.108.2
    AuthenticationMethods publickey
    PasswordAuthentication no
    KbdInteractiveAuthentication no
```
(адрес — collector), `sshd -t && systemctl reload ssh`. Учётка `scanprobe` — без пароля, без sudo, ключ — только
из пары, введённой в Web. Если по SSH отвечает Windows (OpenSSH), цель отклоняется как «неподдерживаемая
платформа» — такой узел собирается по WinRM.

## 13. Склад и выдача оборудования (волна 2) [CI: integration и браузер; на стенде — не проверено]

Раздел Web «Склад». Права: просмотр — все; операции и резервы — оператор и администратор; справочники (склады,
ячейки, места ремонта, каталог), списание и закрытие инвентаризации — администратор.
1. **Справочники:** склад (на площадке) → ячейки внутри склада → место «ремонт» (сервис-центр). Каталог: позиции
   «по серийным номерам» (ноутбуки, мониторы, диски) и «количеством» с единицей (кабель, м; мыши, шт).
2. **Приход:** «Операция» → «Приход» → склад/ячейка → строки: позиция + серийный (+ инв. №) или количество. Если
   экземпляр — это актив реестра, его связь задаётся через API (`asset_uid` в строке прихода).
3. **Выдача / возврат / перемещение / ремонт / установка комплектующего на актив / снятие / списание** — та же
   форма; каждая операция — одна запись журнала с номером акта `ГГГГ-NNNNNN`. Акт открывается сразу; «Печать / PDF»
   — печать браузера (в PDF — «Сохранить как PDF»).
4. **Ошибка в операции** — «Журнал и акты» → «Сторно» с основанием (обратная операция, тоже с актом). Журнал не
   правится. Списание и приход серийных экземпляров не сторнируются.
5. **Резерв** — «Резервы»: экземпляр или количество за сотрудником до срока (1–90 дней); выдать другому нельзя,
   по истечении резерв снимается сам.
6. **Инвентаризация** — «Инвентаризация» → место → «Начать» (движения по месту блокируются) → найденные серийные
   номера списком (сканер штрихкода вводит как текст) и посчитанные количества → «Сохранить факт и сверить» →
   администратор «Закрыть и провести»: акт недостачи (ненайденные — «утерян») и акт излишка. Найденные, но
   числящиеся в другом месте, не перемещаются — оформить перемещение/возврат вручную.
7. **Проверка целостности:** `GET /api/v1/warehouse/verify` (администратор) — остатки должны совпадать с журналом
   (пустой список расхождений). Отчёт «что за кем числится» — «Экземпляры» → фильтр «За кем числится» → CSV.
Финансов (цен, амортизации) в складе нет по решению пользователя (C41).

## 14. Обращения, каталог услуг и портал сотрудников (волна 3) [CI: integration с моком LDAP; на стенде — не проверено]

- **Операторы ИТ** работают в разделе «Обращения»: регистрация инцидента/проблемы, «Взять себе», передача команде,
  переходы состояний (решение обязательно), внутренние и публичные комментарии, связи с активом/сервисом/обращением.
  Для «Взять себе» у пользователя должна быть запись в оргструктуре, связанная с его учётной записью.
- **Сотрудники** входят на портал на той же странице: «Сотрудникам: обращение в ИТ — войти учёткой AD» (логин
  `ivanov`, `DOMAIN\ivanov` или `ivanov@domain`). Условия: настроена синхронизация каталога (раздел «Оргструктура»),
  сотрудник есть в оргструктуре после синхронизации и не отключён в AD. Пароль проверяет каталог; центр пароль не
  хранит. Сотрудник видит только свои обращения и переписку без внутренних комментариев; реестр, склад и очереди ему
  недоступны. Если запись сотрудника уже связана с локальной учёткой оператора — на портал он не входит (оператор
  пользуется обычным входом).
- Все входы на портал — в аудите (`portal.login`); попытки ограничены так же, как обычный вход.
- **Каталог услуг** (C48): «Обращения» → «Каталог услуг» (изменяет администратор). Услуга — название, описание, поля
  формы (строка, текст, выбор из вариантов; обязательные), согласующий (человек или команда — решает любой член
  команды), команда-исполнитель и, для выдачи оборудования, позиция склада. Отключённая услуга на портале не видна.
- **Заявка**: сотрудник на портале выбирает услугу и заполняет форму → «на согласовании» (если задан согласующий) →
  «в исполнении» → «исполнена» → сотрудник подтверждает («Получено» закрывает, «Не выполнено» возвращает в работу).
  Согласующий-сотрудник видит на портале блок «Ждут вашего согласования»; оператор с записью в оргструктуре или
  администратор решает из карточки заявки. Отклонение — только с причиной.
- **Складская услуга** исполняется кнопкой «Выдать и исполнить» в карточке заявки (нужны права на склад): выдача
  выбранного экземпляра заявителю с актом (основание «Заявка REQ-…»), связь заявки с актом и переход «исполнена» —
  одной операцией. Повтор или одновременное исполнение вторым оператором отклоняются, второй выдачи нет.
- **Изменения** (C49): «+ Обращение» → вид «Изменение» → в карточке задать окно (начало, конец, риск, план работ и
  отката) и связи с затронутыми активами/сервисами → «На согласование» → согласует **только администратор** → «Запланировать»
  → «В работу» → «Выполнено…» (результат проверки) или «Откат…» (причина) → «Закрыть». Если окно пересекается с другим
  активным изменением на том же активе/сервисе, карточка показывает пересечения, а планирование требует явного
  подтверждения (отмечается в журнале). Вкладка «Календарь изменений» — окна на две недели с листанием.
- **SLA** (C50): «Обращения» → «SLA» (изменяет администратор): часовой пояс, рабочие дни и часы (один календарь, без
  праздников), порог предупреждения (по умолчанию 80 % срока) и сроки реакции/решения для инцидентов и заявок по
  приоритету P1–P4 в рабочих часах. По умолчанию — пн–пт 09:00–18:00 по Москве. Реакция останавливается при первом
  действии оператора (назначение или переход), решение — при «решено/исполнено/отменено»; «ждём заявителя» и
  согласование заявки — пауза; повторное открытие продолжает срок решения. Очередь показывает худший таймер, карточка —
  оба. Предупреждение и нарушение отмечает фоновая роль (раз в минуту) — в журнале обращения (внутренняя запись).
- **События обращений во внешние системы**: в «Уведомлениях» доступны типы «Новое обращение», «Смена состояния»,
  «Назначение», «SLA: скоро нарушение», «SLA: нарушение срока» (`ticket.*.v1`). В событии — номер, вид, состояние,
  приоритет; тексты обращений не передаются. Повторная доставка несёт тот же `event_id` — получатель отбрасывает дубли.
  Порядок доставки **не гарантирован** (события идут параллельно и с повторами): получатель упорядочивает по
  `aggregate.version` (номер события обращения) или `occurred_at` и хранит обработанные `event_id`.

## 15. Установка collector и агента по коду (C52.01) [CI: integration и браузер; на стенде — не проверено]

1. «Источники данных» → **«Установка»** (администратор): выбрать «collector площадки» или «агент на ПК/сервер»
   (для агента — collector площадки и ОС), число установок (1 или N для массовой раздачи), срок (часы, до 30 суток),
   комментарий → «Создать код». **Код показывается один раз** — в центре хранится только его хеш. Вместе с кодом —
   **отпечаток центра** (SHA-256 сертификата УЦ центра) и готовые команды.
2. Collector (Linux, программа из выпуска):
   `sudo SURVEYSCAN_REGISTRATION_CODE=<код> surveyscan-collector register --center https://<центр> --fingerprint <отпечаток> --dir /etc/surveyscan-collector --state /var/lib/surveyscan-collector`
   → ключи создаются на этой машине, регистрация и enroll в центре, конфигурация `collector.json` и ключи — 0600.
   Затем служба `surveyscan-collector` (deploy/systemd).
3. Агент (через collector площадки — агенту не нужен доступ к центру):
   `sudo SURVEYSCAN_REGISTRATION_CODE=<код> surveyscan-agent register --collector https://<collector>:8443 --fingerprint <отпечаток> --config /etc/surveyscan-agent/agent.json --state /var/lib/surveyscan-agent`
   → затем служба агента.
4. Неверный отпечаток — установка останавливается до отправки кода (защита от подмены адреса). Код неверный,
   просрочен, отозван или исчерпан — «код не принят». Повтор той же установки — «уже зарегистрирована»; если
   оборвалось после регистрации, повторить `enroll --grant-file <state>/registration-grant.json`.
5. В списке кодов: «N из M» — установки (имена машин), «Отозвать» — новые установки по коду отклоняются, уже
   установленные работают. Создание и отзыв — в аудите (`source.registration_code_*`).

## 16. Пакеты и скачивание из Web (C52.04) [CI: контейнеры 8 дистрибутивов, systemd на раннере, Windows Server 2022, браузер; на стенде — не проверено]

1. **Скачать:** «Источники данных» → «Установка» → **«Скачать»** (администратор и оператор): файлы выпуска, который
   работает в центре — агент (Rust) и collector: MSI и zip (Windows x64), deb, rpm, tar.gz (Linux amd64), portable
   одним файлом. Центр отдаёт файл, только если его SHA-256 совпадает с подписанным manifest выпуска; каждое
   скачивание — в аудите (`installer.downloaded`). Подпись manifest центр проверяет ключом
   `SURVEYSCAN_V2_RELEASE_PUBLIC_KEY_FILE` (открытый Ed25519 PEM выпуска); без ключа в Web — «подпись проверяется при
   установке выпуска». Файлы кладёт в выпуск `release.py build --installers .dist/packages` (`make packages`).
2. **Linux (deb/rpm):** `sudo apt install ./surveyscan-agent_*.deb` (или `dnf install ./…rpm`), затем
   `echo <код> | sudo surveyscan-agent-setup --collector https://<collector>:8443 --fingerprint <отпечаток>` — регистрация
   и запуск службы. Массово (Ansible): `/etc/surveyscan-agent/register.env` (`COLLECTOR_URL`, `CENTER_FINGERPRINT`,
   `REG_CODE`; пример — `/usr/share/surveyscan-agent/register.env.example`) до или после установки пакета — служба
   `surveyscan-agent-register` регистрирует один раз и удаляет файл с кодом. Collector — так же
   (`surveyscan-collector-setup --center https://<центр>`, `CENTER_URL`, `LISTEN`). Служба не запускается до регистрации;
   обновление пакета сохраняет регистрацию; `apt purge` удаляет регистрацию, ключи и очередь.
3. **Windows (MSI, тихо или GPO):** `msiexec /i surveyscan-agent_<версия>_windows_x64.msi /qn COLLECTOR_URL=https://<collector>:8443
   CENTER_FINGERPRINT=<отпечаток> REG_CODE=<код>`; collector — `CENTER_URL=…` (и `LISTEN=0.0.0.0:8443`). Ошибка
   регистрации (неверный отпечаток, код, нет связи) — установка откатывается; код в журнал msiexec не пишется.
   Без `REG_CODE` служба ставится, но не запускается: позже `surveyscan-agent register …` и `surveyscan-agent start-service
   --config "%ProgramData%\SurveyScan\agent\config.json"`. Удаление оставляет регистрацию в `%ProgramData%\SurveyScan`;
   `msiexec /x … REMOVE_DATA=1` — удаляет и её. Файлы без подписи Authenticode (решение C52.05): при ручном запуске
   SmartScreen может предупредить — сверьте SHA-256 из Web; для GPO предупреждения нет.
